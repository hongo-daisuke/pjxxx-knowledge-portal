## 総評

全体的によくできている計画書。特に以下の判断は正しい。

- **Phase 0 を独立フェーズとして置いた設計** — CI が一度も回っていない状態でコードを書いても意味がないという認識が 0-1 / 0-2 として最前列に置かれている。これができていないプロジェクトは多い。
- **権限フィルタを Phase 2 の核に据えた判断** — RAG で漏れてはいけない情報がある以上、これが最重要なのは正しい。「全経路で見えないこと」という E2E の書き方も具体的でよい。
- **S3 Vectors → OpenSearch Serverless の出口を Phase 3 に留めた判断** — 移行手順の検証だけ先にやっておいてトリガー条件次第という設計は、コスト管理としてバランスが取れている。
- **リスク表の「フィルタ無し状態を作らない」** — P1 の kb_filter 設計根拠が一行でわかる。

## 気になった点

### 1. Phase 0-1 の完了条件が曖昧 (重要度: 中)

「CI/CD テンプレートの最終検証」は何を確認すれば完了なのかが不明確。

> `npm install` → `eslint .` 実行、CI 全ワークフロー 1 周

と書かれているが、「1 周」がどこまでを指すのか (PR 時の lint/test だけか、dev デプロイまでか) によって作業量が大きく変わる。実作業で「どこまでやったら次に進んでいいか」が判断できない。

**提案**: 完了条件を以下のように具体化する。

```
0-1 完了条件:
- 空の PR を出したとき frontend-ci / backend-ci の全ジョブが緑になる
- dev ブランチへのマージで空の SAM スタックが dev 環境にデプロイされる
- prd 環境デプロイに GitHub Environments の承認ゲートが効いている
```

---

### 2. Phase 2 の作業量が重すぎる (重要度: 高)

2-1 (権限フィルタ) / 2-2 (版管理) / 2-3 (監査ログ) / 2-4 (admin feature) / 2-5 (タグ管理) を 1 フェーズに詰め込んでいるが、これは Phase 1 と同等かそれ以上の開発量になる。「社内展開できる形」というゴールに対して、何が最低条件かを絞り込んでいない。

**影響**: フェーズの完了が遅れると「社内展開ができないまま開発が続く」状態になり、フィードバックループが回らない。

**提案**: Phase 2 を 2 段階に分割する。

| 区分 | 作業 | 根拠 |
|---|---|---|
| **Phase 2-A** (展開最低条件) | 2-1 権限フィルタ完成 / 2-4 admin feature + KB 運用可視化 | これがないと社内展開時に情報漏洩リスクと運用不能のどちらかが生じる |
| **Phase 2-B** (展開後に追加) | 2-2 版管理 / 2-3 監査ログ / 2-5 タグ管理 | 展開を止めずに順次リリースできる |

---

### 3. ADR が「随時」のままになっている (重要度: 低)

S3 Vectors 採用・Retrieve+Converse 採用・Cognito LITE tier 採用など、既に決定済みのアーキテクチャ判断が「ADR は随時」と先送りされている。「随時」は実際には「永遠に書かれない」になりがち。

**提案**: Phase 0-3 の設計書配置タスクと同時に以下の ADR を作成する。

| ADR | 決定内容 |
|---|---|
| ADR-001 | ベクトルストア: S3 Vectors 採用 (OpenSearch Serverless 非採用の理由: アイドル時固定費) |
| ADR-002 | RAG 実装方式: Retrieve + Converse 採用 (Retrieve-and-Generate 非採用の理由: 引用制御) |
| ADR-003 | Cognito tier: LITE 採用 (Essentials 非採用の理由: コスト) |
| ADR-004 | フロントエンド構成: Feature-Based 採用 (Type-Based 非採用の理由: チーム分担・独立性) |
