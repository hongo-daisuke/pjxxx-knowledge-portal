## 指摘 3: `.env` の二重管理 (重要度: 中)

**内容**: `.env.development` / `.env.production` をリポジトリに新規作成する計画だが、テンプレートのデプロイワークフローは **GitHub Secrets から `.env` を生成する方式**。両方が存在すると「どちらが正か」が曖昧になり、環境値の食い違い事故につながる。

**対応 (v2.0)**: Secrets 生成方式に一本化。リポジトリには `.env.example` (実値なし) のみを置き、`.env*` を gitignore。ローカル開発時は各自が `.env.example` から作成する。

**補足**: Cognito クライアント ID や API URL は秘匿情報ではないためコミット運用も技術的には可能だが、その場合はワークフローの `.env` 生成ステップ削除とセットで行う必要があり、テンプレートからの乖離が増えるため採用しない。

## 指摘 4: API ワイヤー形式の不整合 (重要度: 中)

**内容**: 計画の axios インターセプター (camelCase ↔ snake_case 変換) を入れると **API 仕様上のフィールドは snake_case が正** になるが、詳細設計書 (03) の API 例は `docId` 等 camelCase で書かれていた (設計書側の問題でもある)。

**対応 (v2.0)**:
- ワイヤー形式は **snake_case を正** と明記
- 実装前タスクとして「03 詳細設計書の API 例を snake_case に改訂」を計画に追加
- 併せて配置場所を修正: API クライアントは `plugins/axios.ts` ではなく **`shared/api/client.ts`** (規約の 2 レイヤー構成上、API 横断基盤は shared/ が素直。Amplify 初期化のようなアプリ起動系のみ plugins/)

## 補足確認: `kb_filter.py` の P1 配置について (矛盾ではない)

権限フィルタ (F-303) は P2 だが、`kb_filter.py` を P1 の Layer に置くこと自体は正しい。ただし意図を明確化した:

> **P1 でも `visibility = "public"` の固定フィルタを常に適用する。**

これにより P1 期間中に誤って department/private 相当の文書が登録されても、RAG の回答根拠に漏れない (安全側)。P2 ではこのモジュールを orAll 構造 (public ∪ 自部署 ∪ 自分の private) に拡張するだけで済む。
