## 1. DynamoDB 設計

### 1.1 テーブル定義

- テーブル名: `pjxxx-{env}-001-knowledge-main`
- キー: PK (S) / SK (S)、オンデマンドキャパシティ、PITR 有効 (prd)

### 1.2 アイテム設計

| エンティティ | PK | SK | 主な属性 |
|---|---|---|---|
| 文書メタ | `DOC#<docId>` | `META` | title, description, tags[], department, visibility, ownerId, latestVersion, s3Key, fileType, size, status, createdAt, updatedAt |
| 文書版 | `DOC#<docId>` | `VER#<zero-pad version>` | s3Key, uploadedBy, uploadedAt, note, size |
| タグ | `TAG#<tagName>` | `META` | count |
| チャット履歴 | `USER#<sub>` | `CHAT#<ISO8601>` | question, answer, citations[], latencyMs |
| 監査ログ | `AUDIT#<YYYY-MM-DD>` | `TS#<ISO8601>#<uuid>` | userId, action, docId, detail, ttl |

### 1.3 GSI 設計

| GSI | PK | SK | 用途 |
|---|---|---|---|
| GSI1 | `GSI1PK` = `TAG#<tag>` | `GSI1SK` = `UPD#<updatedAt>` | タグ別文書一覧 (更新日降順)。文書メタに tags 分だけ書き込む方式ではなく、タグ→文書の関連アイテム (`TAG#<tag>` / `DOC#<docId>`) を別途作成し GSI1 に射影する |
| GSI2 | `GSI2PK` = `DEPT#<department>` | `GSI2SK` = `UPD#<updatedAt>` | 部署別文書一覧 |

- キーワード検索 (タイトル・説明) は Phase 1 では GSI2/全件 Query 結果へのアプリ側部分一致とする (文書数 数千件想定)。件数増大時は KB の Retrieve をハイブリッド代替として利用
- 監査ログは `ttl` 属性 (登録から 1 年) で自動削除

## 2. API 設計

ベースパス: `/api` (BackendApi)。全 API は Cognito オーソライザ必須。エラー形式はテンプレート共通 (`{"error": {"code", "message"}}`)。

| # | メソッド/パス | 権限 | 概要 |
|---|---|---|---|
| 1 | `POST /documents` | editor | 文書メタ登録 + アップロード用 presigned PUT URL 発行 (Idempotency-Key 必須) |
| 2 | `POST /documents/{docId}/complete` | editor | アップロード完了確定 (S3 HeadObject 検証 → status=active、metadata.json 生成) |
| 3 | `GET /documents` | viewer | 一覧・検索。query: `tag`, `department`, `q`, `next_token`, `limit` |
| 4 | `GET /documents/{docId}` | viewer(権限内) | 詳細 (版一覧含む) |
| 5 | `PUT /documents/{docId}` | editor(所有) / admin | メタ更新 (タグ・公開範囲等) → metadata.json 再生成 |
| 6 | `DELETE /documents/{docId}` | editor(所有) / admin | 論理削除 (status=deleted) + S3 オブジェクト削除 |
| 7 | `POST /documents/{docId}/versions` | editor | 新版アップロード用 presigned PUT URL 発行 |
| 8 | `POST /documents/{docId}/download-url` | viewer(権限内) | presigned GET URL 発行 (有効 5 分) + 監査ログ記録 |
| 9 | `GET /tags` | viewer | タグ一覧 (件数付き) |
| 10 | `POST /chat` | viewer | RAG 質問応答 (Idempotency-Key 必須) |
| 11 | `GET /chat/history` | viewer | 自分のチャット履歴 |
| 12 | `POST /kb/sync` | admin | ingestion job 手動起動 |
| 13 | `GET /kb/status` | admin | 直近 ingestion job の状態・統計 |

### 2.1 代表 API 詳細: `POST /chat`

リクエスト:

```json
{ "question": "経費精算の締め日はいつ?", "session_id": "任意" }
```

処理フロー (`chat-func`):

1. claims から `sub` / `custom:department` / groups を取得
2. メタデータフィルタ式を構築 (基本設計 2.4 の orAll 構造)
3. `bedrock-agent-runtime.retrieve` を実行 (numberOfResults=6, フィルタ適用)
4. 取得チャンク 0 件なら「根拠となる文書が見つからない」旨を返す (LLM は呼ばない)
5. チャンクを根拠コンテキストとして `bedrock-runtime.converse` で回答生成。システムプロンプトで「コンテキスト外の推測禁止・出典番号の明示」を指示
6. citations (doc_id, title, s3_uri, score) を付与してレスポンス。履歴を DynamoDB に保存

レスポンス:

```json
{
  "answer": "経費精算の締め日は毎月25日です [1]",
  "citations": [
    { "doc_id": "d_01H...", "title": "経理規程", "score": 0.72 }
  ]
}
```

### 2.2 presigned URL 方式の詳細

- PUT: `documents-func` が `s3:PutObject` 条件付き (Content-Type / 最大サイズ 100MB) で発行。キー: `documents/<docId>/v<version>/<fileName>`
- 完了確定 API (#2) で HeadObject によりサイズ・存在を検証してから status=active。未確定レコードは TTL で掃除
- GET: 有効期限 5 分。レスポンスヘッダで `Content-Disposition` を付与

## 3. Lambda 設計

共通: Python 3.13 / Powertools (Logger, Metrics) / 環境変数で `TABLE_NAME`, `DATA_BUCKET`, `KB_ID`, `DS_ID`, `MODEL_ID` を注入 / IAM はリソース単位の最小権限 (`${AWS::Partition}` 使用)。

| 関数 | ハンドラ構成 | 主な権限 |
|---|---|---|
| documents-func | APIGatewayRestResolver でルーティング (#1〜#9) | dynamodb (main table + GSI), s3 (DataBucket の documents/* Put/Get/Delete/Head) |
| chat-func | #10, #11 | bedrock:Retrieve (KB ARN), bedrock:InvokeModel (推論プロファイル/基盤モデル ARN), dynamodb |
| kb-sync-func | S3 イベント / EventBridge / #12, #13 | bedrock:StartIngestionJob, bedrock:GetIngestionJob, bedrock:ListIngestionJobs (KB/DS ARN), dynamodb (同期状態) |

### 3.1 Idempotency

- 対象: `POST /documents` (二重登録防止), `POST /chat` (二重課金防止)
- Powertools Idempotency ユーティリティ + 専用 DynamoDB テーブル (テンプレート標準構成)。キーはヘッダ `Idempotency-Key`

### 3.2 metadata.json 生成仕様

`documents/<docId>/v<version>/<fileName>` に対し、同一プレフィックスへ `<fileName>.metadata.json` を生成する:

```json
{
  "metadataAttributes": {
    "docId": "d_01H...",
    "title": "経理規程",
    "visibility": "department",
    "department": "keiri",
    "ownerId": "cognito-sub",
    "tags": "経理,規程"
  }
}
```

- 属性値は文字列/数値のみ (リストは KB 側制約に合わせカンマ結合)
- メタ更新 (#5) 時は最新版のサイドカーを再生成し、次回同期で反映

## 4. フロントエンド設計

### 4.1 画面一覧

| 画面 ID | 画面名 | ルート | 主要コンポーネント |
|---|---|---|---|
| SC-01 | ログイン (Hosted UI リダイレクト) | `/login` | — |
| SC-02 | 文書一覧・検索 | `/documents` | DocumentTable, TagFilter, SearchBar |
| SC-03 | 文書詳細 | `/documents/:id` | DocumentDetail, VersionList, DownloadButton |
| SC-04 | 文書登録・編集 | `/documents/new`, `/:id/edit` | DocumentForm, UploadDropzone (editor 以上) |
| SC-05 | RAG チャット | `/chat` | ChatWindow, CitationCard, HistoryDrawer |
| SC-06 | 管理 (同期状態・タグ・監査) | `/admin` | SyncStatusPanel, TagManager, AuditTable (admin) |

### 4.2 ディレクトリ構成・状態管理

- テンプレートの `vue-directory-structure` 規約に従い **Feature-Based** を採用する (`features/documents|chat|auth|admin` + `shared/`)。feature 間の直接 import は禁止し、共有物は `shared/` に昇格 (詳細は 06 フロントエンド構成図 §2)
- Pinia ストアは各 feature 配下に置く。ただし認証情報は全 feature から参照するため `shared/stores/useAuthStore` (claims・ロール・部署) に配置する (feature 間 import 禁止の規約に従い `shared/` へ昇格)。`features/documents/stores` (一覧・検索条件・ページング), `features/chat/stores` (会話・履歴)
- API クライアントは `shared/api/client.ts` に集約し、トークン付与・401 時の再ログイン誘導を共通化。各 feature の `services/` はこれを利用する
- ルートガード: `meta.requiredRole` を定義し、editor/admin 画面を制御 (最終判定はサーバ側)

### 4.3 アップロード UX

1. フォーム入力 → `POST /documents` → presigned URL 取得
2. ブラウザから S3 へ直接 PUT (進捗バー表示)
3. `POST /documents/{id}/complete` → 「同期待ち」バッジ表示 (KB 反映まで最大 15 分の旨をツールチップ表示)

## 5. エラー・ログ設計

| 種別 | 方針 |
|---|---|
| API エラー | 400 (バリデーション) / 403 (権限) / 404 / 409 (Idempotency 競合) / 500。詳細メッセージはログのみ、クライアントには汎用文言 |
| RAG 特有 | 検索 0 件: 200 で `answer=null` + 案内文言。モデルスロットリング: 429 + リトライ案内 |
| ログ | Powertools Logger (JSON 構造化、correlation_id = API GW requestId)。監査系操作は CloudWatch とは別に DynamoDB 監査ログへ二重記録 |
| メトリクス | ChatRequests, ChatNoHit, IngestionJobFailed をカスタムメトリクス化し、prd はアラーム設定 |

## 6. テスト観点 (抜粋)

| 区分 | 観点 |
|---|---|
| 単体 (pytest) | フィルタ式構築 (部署・private の組合せ)、presigned 条件、Idempotency |
| 結合 | S3 イベント → 同期起動、メタ更新 → サイドカー再生成 |
| E2E (Playwright) | viewer/editor/admin の 3 ロールで、権限外文書が一覧・詳細・チャット出典に現れないこと |
| セキュリティ | JWT 無し/改ざん、他人の private 文書 ID 直叩き、presigned URL 期限切れ |
